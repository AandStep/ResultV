# Детерминированный CA + обнаружение дублей

**Дата:** 2026-07-23
**Ветка:** android
**Статус:** дизайн одобрен, ожидает плана реализации

## Проблема

Корневой CA для browser MITM ad-block (`ca.crt` + `ca.key`) генерируется в
`dataDir/filter/` — приватном хранилище приложения (`internal/filter/ca/ca.go`,
`EnsureRoot`). При удалении приложения это хранилище стирается.

Последствия переустановки:

1. `EnsureRoot` не находит `ca.crt` → генерирует **новый** случайный корневой ключ.
2. Старая запись CA в системном хранилище доверия Android остаётся
   (пользовательские CA живут отдельно от приложения и переживают удаление), но
   больше не совпадает байт-в-байт с новым CA → `CertStore.isInstalled`
   возвращает `false`, приложение считает CA неустановленным.
3. Пользователь устанавливает новый CA → в системе копится дубль
   «ResultV AdBlock Root CA».
4. MITM может ломаться: доверенный старый CA не подписывает новые leaf-сертификаты.

Из системного хранилища доверия нельзя достать приватный ключ (там только
сертификат), поэтому переиспользовать уже установленный CA напрямую нельзя — его
ключ должен пережить переустановку.

## Цель

Сделать переустановку полностью прозрачной: приложение воссоздаёт **байт-в-байт
тот же** корневой CA, что уже установлен в системе. Ноль действий пользователя,
ноль новых дублей. Дополнительно — подсветить уже накопившиеся дубли.

## Решение

Детерминированная генерация CA из стабильного seed (`ANDROID_ID`), который
переживает переустановку при неизменной подписи приложения.

### 1. Детерминированная генерация CA (Go)

`internal/filter/ca/ca.go` — `EnsureRoot` получает второй аргумент `seed string`:

- Файлы на диске есть → `loadRoot` как сейчас (быстрый путь, seed игнорируется).
- Файлов нет и `seed != ""` → **детерминированная** генерация:
  - DRBG = детерминированный поток байт из
    `HKDF-SHA256(secret=seed, salt="resultv-ca-v1", info="rsa-2048")`,
    обёрнутый в `io.Reader`.
  - `rsa.GenerateKey(drbg, 2048)` → тот же ключ при том же seed.
  - `SerialNumber` = 16 байт из того же потока (не `crypto/rand`).
  - `NotBefore` / `NotAfter` = **фиксированные** константы, не `time.Now()`
    (напр. 2020-01-01T00:00:00Z … 2040-01-01T00:00:00Z).
  - RSA-подпись (PKCS#1 v1.5) детерминирована → итоговый DER-сертификат
    байт-в-байт одинаков при одинаковом seed.
- Файлов нет и `seed == ""` → текущая случайная генерация (fallback).

Порядок потребления байт из DRBG (ключ → serial) фиксирован и является частью
контракта: менять его нельзя, иначе воспроизведение сломается.

**Принятый риск:** детерминированная генерация — резервный путь; в норме
`ca.key` лежит на диске и просто загружается. Детерминизм зависит от реализации
`rsa.GenerateKey` в текущей версии Go. Крупный апгрейд Go теоретически может
изменить вывод из того же seed. В этом случае после переустановки поведение
деградирует до текущего (потребуется переустановить CA) — не хуже статус-кво.
Это осознанный компромисс ради простоты; альтернатива (собственная генерация
простых чисел RSA) отвергнута как чрезмерно рискованная.

### 2. Проброс seed (Kotlin → Go)

- Kotlin читает `Settings.Secure.ANDROID_ID`. Значение стабильно для пары
  (подпись приложения, пользователь) на устройстве и переживает
  uninstall/reinstall. Меняется только при factory reset или смене подписи —
  тогда всё равно нужен новый CA.
- Новый mobile-API `Mobile.setFilterCASeed(dataDir, seed)` сохраняет seed в
  `filter.Manager` (новое поле) до первого обращения к CA.
- `FilterCARootPath` / `CARootPath` используют сохранённый seed при вызове
  `EnsureRoot`.
- `ANDROID_ID` пустой/недоступен (редкий мультиюзер-кейс) → `setFilterCASeed`
  не вызывается или получает `""` → fallback на случайную генерацию.

**Порядок вызова:** Kotlin вызывает `setFilterCASeed` до первого обращения к CA
(`CertStore`, wizard, `FilterProxyWatchdog`). Точная точка внедрения
определяется на этапе плана реализации.

### 3. Обнаружение дублей (Kotlin, `CertStore`)

- Новый метод `CertStore.staleEntryCount(dataDir): Int` — считает
  пользовательские CA (`user:*`) с Subject CN `"ResultV AdBlock Root CA"`,
  которые **не** байт-равны текущему нашему CA. Это устаревшие дубли.
- Wizard / Settings: если `staleEntryCount > 0` → баннер
  «В системе N старых сертификатов ResultV, удалите лишние» + кнопка-диплинк в
  *Settings → Trusted credentials → User*
  (`Settings.ACTION_SECURITY_SETTINGS`; удалить CA программно Android не даёт).
- Строки локализуются (`strings.xml`, существующий паттерн wizard-экрана).

### 4. Совместимость с текущей установочной базой

У пользователей с уже установленным **случайным** CA при следующей переустановке
появится один детерминированный дубль (одноразово). Его подсветит баннер из п.3;
пользователь удалит лишнее вручную. Дальнейшие переустановки прозрачны.

## Тестирование

**Go (`internal/filter/ca/ca_test.go`):**

- Два вызова `EnsureRoot(dir, seed)` с чистой директорией и одинаковым seed →
  идентичные байты cert **и** key.
- Разные seed → разные CA.
- Пустой seed → валидный CA (случайный путь, current behaviour сохранён).
- Serial и даты валидности детерминированы при фиксированном seed.
- Существующий `TestManager_CARootPath_ReturnsExistingFile` продолжает проходить.

**Kotlin (`CertStoreTest` в стиле существующих тестов):**

- `staleEntryCount` корректно считает записи ResultV, не равные текущему CA, при
  подставном/фейковом trust store.

## Затрагиваемые файлы

- `internal/filter/ca/ca.go` — сигнатура `EnsureRoot`, детерминированная ветка,
  DRBG-хелпер.
- `internal/filter/manager.go` — поле seed, сеттер, проброс в `CARootPath`.
- `mobile/libbox.go` — `SetFilterCASeed`, использование seed в `FilterCARootPath`.
- `android/.../vpn/CertStore.kt` — `staleEntryCount`, вызов `setFilterCASeed`.
- `android/.../ui/screens/CertWizardScreen.kt` (+ Settings) — баннер о дублях.
- `android/.../res/values/strings.xml` — строки баннера.
- Тесты: `internal/filter/ca/ca_test.go`, Kotlin `CertStoreTest`.

## За рамками (YAGNI)

- Программное удаление системных CA (Android не разрешает).
- Резервное копирование ключа через Android Auto Backup (отвергнуто как
  ненадёжное).
- Миграция уже установленных случайных CA к детерминированным (невозможно без
  приватного ключа старого CA).
