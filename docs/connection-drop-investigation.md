> Handoff-документ для продолжения в новом чате. Описывает симптом, что проверено,
> что починено, что показал git/конфиг-дифф и что ещё НЕ проверено.
> Дата: 2026-06-15. Ветка: `dev`. Все правки в рабочем дереве **не закоммичены**.

## 1. Симптом (главная нерешённая проблема)

- В туннель-режиме **разом, в один и тот же миг, умирают ВСЕ активные соединения** сессии
  (возраст от пары секунд до десятков минут — т.е. рвётся всё, что было открыто с момента connect).
- В логах sing-box это:
  ```
  [SING-BOX] ERROR[...] connection: connection upload closed: read tcp4 172.19.0.1:<fixedport>->172.19.0.2:10XXX: wsarecv: An established connection was aborted by the software in your host machine.
  ```
  - **Доминирует `WSAECONNABORTED`** — «aborted by the software in your host machine» = **локальный** обрыв (таймаут/локальный teardown), НЕ сервером.
  - Меньшая часть — `WSAECONNRESET` («forcibly closed by the remote host»).
  - Адреса `172.19.0.1 ↔ 172.19.0.2` — это внутренняя /30 TUN-инбаунда (`address: 172.19.0.1/30`), т.е. tun-сторона проксируемых соединений.
- **Триггер: ТОЛЬКО моя (Claude Code) активная работа** — `go test`/`go build`, git, фетчи, т.е. всплески CPU + процессов + DNS-резолвов. **В браузере (даже под нагрузкой) НЕ воспроизводится.**
- **Воспроизводится на ВСЕХ протоколах**: Hysteria2, VLESS, AmneziaWG (AWG).

### Решающий бисект (сделал пользователь, даунгрейдом установленного приложения)
- **3.2.1 — НЕ падает** под той же нагрузкой, на **том же** Hy2-сервере.
- **3.2.2 и новее — падает.**
- Подтверждено несколько раз, на одном и том же сервере Hy2. То есть регрессия внесена в **3.2.2**.

### Чем я генерил нагрузку (для повторения)
`go test ./...` в фоне + 3–4 параллельных `WebFetch` по разным хостам + `WebSearch`.
⚠️ ВАЖНО: `WebFetch`/`WebSearch` в Claude Code исполняются **на стороне Anthropic**, НЕ через туннель пользователя.
Через туннель из «моей нагрузки» реально идёт: локальный `go test ./...` (CPU-компиляция + DNS + докачка модулей)
и долгоживущий стриминговый коннект Claude Code ⇄ `api.anthropic.com`. Значит решающий фактор — локальная
CPU/DNS/процесс-нагрузка от `go test`, а не сами фетчи.

## 3. Что ПОЧИНЕНО (правки в рабочем дереве, НЕ закоммичены, тесты зелёные)

### Фикс A — залипший TUN/Wintun-адаптер (отдельный реальный баг, из первых логов)
Симптом тех логов: `open interface take too much time` → `configure tun interface: The system cannot find the file specified`,
помогал только ребут. Причина: восстановление снимало только маршруты/DNS, но мёртвое устройство Wintun
(`sing-tun Tunnel`) оставалось, и retry переоткрывал дохлый адаптер.
- `internal/proxy/systun_windows.go`: `staleTunRemovalScript()` + `removeStaleTunAdapter()` — сносят PnP-устройство
  `sing-tun Tunnel` через `pnputil /remove-device` (admin напрямую, иначе через elevated UAC), строгий матч по описанию.
- `internal/proxy/systun.go` / `systun_other.go`: индирекция `removeStaleTunAdapterFn` + no-op заглушка.
- `internal/proxy/manager.go` (`startEngine`): при транзиентной TUN-ошибке перед retry удаляем устройство.
- Тесты: `manager_tunretry_test.go`, `systun_windows_test.go` (6 шт.) — зелёные.
- **Статус: валиден, оставляем.** К главному багу (обрывы под нагрузкой) отношения не имеет.

### Фикс B — server-IP pinning на ОДИН IP (регрессия 3.2.4, `da5ae2c`)
В `outbound.go` домен сервера подменялся одним IPv4 → сессия прибита к одному бэкенду CDN; его сброс ронял всё,
и sing-box не переразрешал. Сделал «мульти-IP hosts-пин»:
- `engine.go`: поле `ProxyConfig.ResolvedIPs []string`; `SBDNSServer.Predefined`; хелпер `serverPinnedIPs`;
  в `buildDNS` домен сервера резолвится из статического `hosts`-сервера `server-pin` со ВСЕМИ IP; route-exclude по всем IP.
- `outbound.go`: **убрана** подмена `out.Server = ResolvedIP` (остаётся домен → sing-box снова делает фейловер).
- `manager.go`: `resolveAllServerIPs()`, заполнение `ResolvedIPs` на обоих connect-путях, синк в watchdog.
- `singbox.go`: редакция логов прячет все бэкенды.
- `internal/system/killswitch.go`: `resolveProxyIPs` принимает список IP через запятую (чтобы фаервол пускал все бэкенды и не было дедлока kill-switch при фейловере).
- `app.go`: engage-колбэк kill-switch отдаёт все запиненные IP.
- Тесты: `server_pin_test.go`, `udp_quic_smoke_test.go` (включая strict-decode `hosts/predefined` ядром) — зелёные.
- **Статус: валиден, оставляем.** НО к главному багу отношения **не имеет**: подтверждено по живому конфигу пользователя
  (`h2-config.json`), что его Hy2-сервер `k.sunsetglow.today` резолвится в **один** IP `152.53.33.10` — фейловерить
  всё равно некуда, и фикс деплоится корректно, но обрыв не лечит.

### Откат — NAT-ключи `udp_timeout`/`endpoint_independent_nat` (ложная гипотеза)
Была теория, что для не-WG протоколов вредны `udp_timeout: "30s"` + `endpoint_independent_nat: true` на TUN-инбаунде
(их в 3.2.2 отключили для WG/AWG). Я их убрал для всех протоколов, но **пользователь сообщил, что AWG тоже падает**
(хотя у AWG этих ключей нет) → гипотеза неверна → **изменение откатил** (вернул как было: `engine.go` `if pt != WIREGUARD && pt != AMNEZIAWG { tun.UDPTimeout="30s"; tun.EndpointIndependentNat=true }`, и тест `TestTunInboundUDPTimeoutShapeSmoke` вернул к проверке наличия ключей).
